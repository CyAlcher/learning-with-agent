## 一、先回答核心困惑：为什么理论 5 步，代码却一堆函数？

**一句话：理论 5 步是「菜谱」，代码是「后厨」。**

| | 理论（菜谱） | 代码（后厨） |
|---|---|---|
| 粒度 | 5 个动作：选/跑/反思/变异/收 | 每个动作展开成多个函数 |
| 为什么展开 | 人脑理解的最小动作集 | 要处理工程细节：去重/批处理/缓存/采轨迹/回调/计数 |

**举例：「②跑 Execute」理论就一个词，代码里是 5 件事**（都在 `reflective_mutation.py` 的 `propose()` 里）：

```python
# 1. 去重：同一个候选被多个任务选中，不重复评估
unique_keys.setdefault(key, (task.parent_candidate, task.minibatch))   # :327

# 2. 批处理：一批候选一起评估
parent_evals = self._batch_evaluate(items)                              # :350

# 3. 采轨迹：capture_traces=True 采集 side_info（ASI）
invoke_batch_evaluate(self.adapter, items, capture_traces=True)        # :280

# 4. 缓存：评估过的缓存，不重复算
state.evaluation_cache.put_batch(...)                                   # :383

# 5. 计数：统计花了多少评估（预算）
state.increment_evals(total_parent_evals)                               # :376
```

所以「跑」这 1 个理论步 = 代码里 5 个函数。**理论 5 步 ≠ 5 个函数，是 5 个动作 → N 个函数**。这就是你「看不懂」的根：你拿「5 步」去套代码，当然对不上——代码是 5 步的「工程展开」，多出来的全是工程细节，不是新概念。

## 三、两个「是啥」（Max 问的）

**① ReflectiveMutationProposer 是啥？** 类名拆开 = `Reflective`(反思式) + `Mutation`(变异) + `Proposer`(提议器) = **「反思式变异提议器」**。它就是理论里「反思+变异」两步合并后的实现类，负责生成新候选。文件 `reflective_mutation.py` 是它的实现。

**② 为什么 5 步落在 2 个类？**（回应「一句话闭环不一致」）
- `ReflectiveMutationProposer` 管 **前 4 步**（选/跑/反思/变异）= **「生成」**候选的职责。
- `GEPAEngine` + `acceptance_criterion` 管 **第 5 步**（收）= **「筛选」**候选的职责。

这是「生成 vs 筛选」的职责分离。所以 5 步 → 2 个类，不是不一致，是**「生成 4 步 + 筛选 1 步」**的工程切分。

## 四、出题逻辑（为什么是这 5 题）

**5 题 = 5 步的「最小代码锚点」**，每题对应一步或一个数据流源头：

| 题 | 对应理论 | 为什么选它 |
|---|---|---|
| 1 evaluator 返回 | score vs side_info 数据流源头 | 它是「evaluator 返回两样」的唯一代码证据 |
| 2 capture_traces | ②跑 Execute | 「采轨迹=采 ASI」的最直接一行 |
| 3 make_reflective_dataset | ③反思前置 | 「把评估结果打包给 LLM 诊断」的入口 |
| 4 reflect | ③④反思+变异合并 | 「反思和变异同一次调用」的唯一证据 |
| 5 acceptance_criterion | ⑤收 Accept | 「变好才收」的唯一代码证据 |

选这 5 题 = 用 5 行代码钉住 5 个理论概念，是最短「看代码 → 认出理论」的路径。

### 题 1（数据流源头）：evaluator 返回几样？
```python
# 绝对路径：week26/gepa_space/scripts/run_blackbox.py:64
return result["score"], side_info   # side_info 含 error/traceback/stdout = ASI
```
→ 返回两样：`score`(标量=好坏→选/收) + `side_info`(ASI=为什么坏→反思)。等价「loss/reward 值 + 梯度方向」。

### 题 2（②跑）：capture_traces 采什么？

→ 采执行轨迹 trajectories(=ASI)，对应②跑捕获轨迹；「没轨迹就跳过反思」印证**反思依赖 ASI**。

### 题 3（③反思前置）：make_reflective_dataset 对应哪步？
```python

```
→ 对应③反思前置：把 `eval_curr`(scores+trajectories) 打包成「反思数据集」= 把 side_info 整理成 LLM 能读的形式。

### 题 4（③④合并）：reflect 对应哪步？反思/变异分开还是合并？
```python
# reflective_mutation.py:188
proposal, next_lm = self._reflection_lm.reflect(candidate, reflective_dataset, components_to_update)
```
→ 对应③反思+④变异，合并成一次 `reflect()` 调用：LLM 读 reflective_dataset 诊断 + 同时生成 `proposal`。印证「反思和变异同一次调用」。

### 题 5（⑤收）：acceptance_criterion 对应哪步？StrictImprovement 语义？

```python
self.acceptance_criterion = acceptance_criterion or StrictImprovementAcceptance()
```

→ 对应⑤收 Accept：StrictImprovement = 子候选分数必须**严格 >** 父候选才进帕累托前沿，否则丢弃。
